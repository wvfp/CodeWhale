# CodeWhale 网络小说创作平台改造方案

## 一、背景与目标

### 1.1 调研发现

当前主流AI写小说工具分为几类：

| 工具 | 特点 | 优势 | 劣势 |
|------|------|------|------|
| 笔灵AI | 全流程网文辅助 | 懂网文节奏、题材库全 | 同质化严重 |
| 扣子App | 项目空间+多Agent | 长期连载一致性好 | 重客户端 |
| NovelWeave | VSCode插件+方法论 | 结构化创作 | 偏技术向 |
| FeelFish | 桌面客户端 | 智能上下文总结 | 生态封闭 |
| AI千集 | Skill化能力 | 专业风格控制 | 偏向短篇 |

### 1.2 改造目标

将CodeWhale改造为**一站式网络小说创作平台**，核心优势：
- 利用CodeWhale已有的Skill、Sub-agent、MCP能力
- 项目化管理 + 终端原生体验
- 支持多人协作和多设备同步
- 长篇连载一致性保证

## 三、核心功能模块

### 3.1 Skill体系设计

#### 3.1.1 主Skill - `novel-writer`
- **职责**：项目管理、流程引导、命令分发
- **核心能力**：
  - 项目初始化和配置
  - 创作阶段管理（世界观→人设→大纲→正文→润色）
  - 一致性检查触发
  - 子Skill协调

#### 3.1.2 子Skill矩阵
| Skill名称 | 功能 | 适用场景 |
|-----------|------|----------|
| `world-builder` | 世界观构建 | 设定世界规则、力量体系 |
| `character-designer` | 人物设计 | 创建和管理人物档案 |
| `outline-planner` | 大纲规划 | 总纲、分卷、章节规划 |
| `chapter-writer` | 章节写作 | 正文创作、续写、扩写 |

| `plot-twist-master` | 爽点设计 | 高潮设计、反转规划 |
| `pacing-controller` | 节奏控制 | 调整章节节奏、信息释放 |

## 四、关键技术实现

### 4.1 基于Constitution的一致性保证

利用CodeWhale已有的Constitution机制，为每个小说项目创建专属宪章：

```markdown
# 小说创作宪章

## 不可违背的设定
1. 主角张三是左撇子
2. 这个世界没有电
3. 修炼等级：炼气→筑基→金丹→元婴

## 文风要求
- 短句为主，节奏明快
- 避免"然而"、"此外"、"总的来说"
- 对话要口语化

## 节奏规则
- 每章结尾必须留钩子
- 每3章一个小高潮
- 每10章一个大高潮
```

### 4.2 Sub-agent协作模式

利用CodeWhale的Sub-agent能力，实现多Agent协同创作：

```
主Agent (novel-writer)
├── 世界观Agent (world-builder)
├── 人设Agent (character-designer)
├── 大纲Agent (outline-planner)
├── 写作Agent (chapter-writer)
└── 审核Agent (consistency-guard) ← 只读检查
```

### 4.3 Memory系统增强

为小说创作定制Memory：
- **关键设定记忆**：自动提取和总结世界观、人设
- **情节记忆**：记录已发生的关键事件
- **伏笔追踪**：自动追踪埋设的伏笔，提醒回收
- **风格记忆**：学习用户的写作偏好

### 4.4 MCP服务集成（可选扩展）

| MCP服务 | 功能 |
|---------|------|
| `novel-db` | 小说数据库查询（参考爆款） |
| `name-generator` | 人名、地名生成 |
| `market-analysis` | 网文市场分析 |
| `publishing` | 一键发布到平台 |

## 五、工作流程设计

### 5.1 五阶段创作流程

```
阶段一：世界观构建
    ↓
阶段二：人物设计
    ↓
阶段三：大纲规划
    ↓
阶段四：正文写作
    ↓
阶段五：修改润色
```

每个阶段都有明确的验收标准，必须完成前一阶段才能进入下一个阶段（可配置跳过）。

### 5.2 章节创作工作流

```
1. 读取细纲 + 前文回顾
    ↓
2. 确认关键情节点
    ↓
3. 生成初稿（用户可打断）
    ↓
4. 用户编辑修改
    ↓
5. 一致性检查（自动）
    ↓
6. 润色优化
    ↓
7. 保存并更新记忆
```

## 八、讨论议题

### 8.1 界面选择
- **纯TUI**：符合CodeWhale终端原生风格，但学习曲线陡
- **TUI + Web**：TUI创作 + Web可视化，体验更好但复杂
- **IDE集成**：VSCode/Nvim插件，受众更广但偏离定位

### 8.2 AI角色定位
- **纯助手**：只提供建议，不直接生成
- **协同创作**：AI生成 + 用户编辑
- **代笔模式**：AI全自动生成（需用户确认）

### 8.3 数据存储
- **纯文件**：简单、透明、Git友好
- **SQLite索引**：查询更快但增加复杂度
- **混合方案**：文件为主，SQLite索引为辅

### 8.4 扩展性
- 是否支持自定义Agent？
- 是否开放MCP协议给第三方？
- 是否需要插件市场？

## 十一、新增案例分析与改进方向

### 11.1 新案例关键特性分析

#### 11.1.1 一致性保障技术

| 工具 | 核心技术 | 效果 | 我们可以借鉴 |
|------|---------|------|------------|
| **Novarrium** | 结构化事实追踪 + 不可变事实锁定 + 主动一致性执行 + 自动事后验证 | 25章测试中唯一通过的工具 | ✅ 需重点实现：**主动执行而非被动引用** + **不可变设定标记** |
| **FeelFish** | 智能上下文管控（自动记忆设定、章节、情节） | 3万字后人设偏差率 <5% | ✅ **自动提取结构化事实**而非纯文本记忆 |
| **唐库** | 全自动生成 + 精细化调校双引擎 | 百万字无逻辑断层 | ✅ 双模式：快速生成 + 精细调校 |

#### 11.1.2 多模型分工策略（2026最新趋势）

根据 Inkfluence AI 测试，不同模型有不同专长：

| 任务 | 最佳模型 | 我们的设计 |
|------|---------|----------|
| 散文/文风 | Claude Opus 4.7 | 润色阶段用 Claude |
| 情节逻辑 | GPT-5 | 大纲/情节规划用 GPT-5 |
| 长上下文 | Gemini 2.5 Pro | 回顾/一致性检查用 Gemini |
| 快速草稿 | Claude Sonnet 4.5 / GPT-4o | 正文生成用性价比高的模型 |

**结论**：我们需要支持**任务级模型路由**，不同阶段用不同模型。

#### 11.1.3 创作流程创新

| 工具 | 创新点 | 借鉴价值 |
|------|--------|---------|
| **NovelHive** | 7阶段流水线 + 不同模型负责不同阶段 + 完整交付（封面+音频） | ⭐⭐⭐⭐⭐ 多阶段流水线设计 |
| **NovelistAI** | 整章生成 + 页面删除 + 重写 + 精确编辑（局部修改） | ⭐⭐⭐⭐ 细粒度编辑控制 |
| **Sudowrite Muse** | 专门训练去除陈腐表达的小说专用模型 | ⭐⭐⭐⭐ 垂直领域模型/提示词 |
| **文心创作** | 多情节方案（3套）+ 多风格一键转换 + 读者偏好预测 | ⭐⭐⭐ 分支探索功能 |

### 11.2 方案改进方向（基于新案例）

#### 改进方向1：一致性保障升级（最高优先级）

**当前设计**：Constitution + Memory + 定期检查  
**改进后**：

```
┌─────────────────────────────────────────────────────────┐
│  主动一致性保障系统                                     │
├─────────────────────────────────────────────────────────┤
│  1. 不可变事实锁定 (Immutable Facts)                    │
│     - 用户标记"绝对不能改"的设定                          │
│     - 任何生成都必须通过这些事实的约束检查                  │
│                                                          │
│  2. 结构化事实数据库 (Structured Fact DB)               │
│     - 自动从文本中提取事实（角色、事件、关系）              │
│     - 用户可查看、编辑、验证AI"知道"什么                  │
│                                                          │
│  3. 事前约束 + 事后验证                                  │
│     - 生成前：主动注入约束条件                            │
│     - 生成后：自动扫描一致性问题并标记                    │
│                                                          │
│  4. 一致性评分系统                                       │
│     - 每章生成后给出一致性评分（0-100分）                 │
│     - 指出具体问题位置和建议修复方案                      │
└─────────────────────────────────────────────────────────┘
```

**新增命令**：
```bash
/fact lock [description]      # 锁定不可变事实
/fact list                     # 查看所有结构化事实
/fact verify                   # 验证事实一致性
/consistency score             # 检查当前章节一致性评分
```

**项目结构更新**：
```
my-novel/
├── .novel/
│   ├── facts.json            # 结构化事实数据库（新增）
│   ├── immutable-facts.md    # 不可变事实（新增）
│   └── ...
└── ...
```
